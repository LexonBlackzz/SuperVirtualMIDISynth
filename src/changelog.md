# SVMS V3 — running changelog

Low-key running log, updated with every landed change. The root
`CHANGELOG.md` carries the polished per-version entries I publish when I cut
a release; this file is where changes land first, raw, under "Unreleased",
until I move them into a release section.

Format: newest first, one bullet per landed change, matching the commit's
`type(v3): one-liner` style plus a line of context where it helps.

## Unreleased

- 2026-10-31 `perf(v3): volume and pan ops ride the AVX2 kernels as a per-channel gain curve instead of cutting every voice` - the Noise Challenge 2 window (10.5-14.1 s) carries about 245 volume/pan/bend controllers per 441-frame block, and every volume or pan op was applied to every voice of its channel and cut that voice's span, so a heavy block paid (voices x ops) applications plus as many kernel entries. Dropping only the mix ops in an experiment took one-thread heavy blocks (5000+ events) from 865% to 472% of the block time, so the mix ops were more than half of them. Now the plan builds, once per block per channel, the mix scale in force at every frame (a few floats per frame); the single-voice AVX2 sustained, release and attack/decay kernels read it per chunk (the voice's gainLeft/gainRight times the curve value, the same product a mix op left in the row, then times currentGain for the sustained kernel: the same order and rounding, so the audio is bit-identical to splitting), the row keeps the volume/pan of its last frame afterwards, and everything else (other backends, vibrato channels, a voice launched on the frame of a mix op, spans the kernels refuse) splits at the ops as before. `SetBendFusion(false)` brings the old path back. `TestStepBreakKernels` now also covers the curve (912 sustained and release cases per seed, four seeds, bit for bit against the span split at the op frames, and against the scalar span for the cases that used to differ) and `TestBendFusionIdentity` mixes 40 volume/pan CCs per block in with the bends. Same window, GeneralUser GS, callback load p95 / p99: 16384 voices 69 / 93 -> 64 / 86, 32768 voices 124 / 168 -> 111 / 137, 131072 voices 420 / 548 -> 317 / 382, 262144 voices 770 / 1099 -> 553 / 671; one thread, heavy blocks 865% -> 564%, 20 threads 111% -> 94%. The chopped-notes bench without controllers is about 6% slower in its median (2.9 -> 3.1 at 5000 voices, 6 threads); I did not chase that because no real file I have is free of controllers.

- 2026-10-31 `fix(v3): the release and attack/decay chunk kernels store the cursor wrapped` - found while extending the step-break test to more random seeds: a releasing voice whose span ran through the chunk kernel could leave its cursor past the loop end (the wrap happens at the top of the next chunk iteration, which never came), and the next span, when it was 1-4 frames, read its first frame from the sample data after the loop instead of from the loop start: one wrong frame (a click) per occurrence, with no tolerance to hide it; the sustained kernel already stored the wrapped cursor. Both templates now wrap before storing, like the sustained one and the scalar span. This is an audible correction for released voices that hit the case (long events-per-block material), not a change of the intended sound.

- 2026-10-31 `test(v3): SVMS_BLOCK_CSV for the offline song tool` - `svms_v3_midi_song` writes one line per block (frame, events, active voices, callback load percent) to the path in the variable; it is how I found that the heavy blocks of the Noise Challenge 2 window correlate 0.96 with the number of events in the block.

- 2026-10-31 `perf(v3): a channel volume/pan op costs a few multiplies per voice, not a sqrt and a second powf` - in the same Noise Challenge 2 window, with GeneralUser GS, a profile of the busiest render thread at 262144 voices put 49% in applying channel ops to the voices (about 245 CC/bend ops per 441-frame block, each applied to every voice of the channel, with a `sqrt` for the steal output gain per op, and a bend op evaluating its `powf` a second time inside the apply). The steal output gain is only read when the plan picks a victim, never between the ops of one block, so only the last mix op of the channel computes it (ghost rows still compute it every time), and the apply takes the bend ratio the caller already computed. Same values at the end of the block. That share fell from 49% to 2% in the profile. Noise Challenge 2 window, 441-frame blocks, callback load p95 / p99: 16384 voices 84 / 116 -> 69 / 93, 32768 voices 138 / 176 -> 124 / 168, 131072 voices 597 / 728 -> 420 / 548, 262144 voices 1609 / 2144 -> 770 / 1099.

- 2026-10-31 `perf(v3): the 8-sample voice filter keeps its coefficients and state in registers` - profiling Paprika's Noise Challenge 2 (10.5-14.1 s) with my Kryo Keys sfz showed 65% of the busiest render thread inside the per-voice low-pass: the time-chunk kernels ran it one sample at a time through the voice arrays, so every sample loaded z1/z2 that the previous sample had just stored (a store-forward on the recursive chain). The eight samples now load a0/b1/b2/z1/z2 once, run the same arithmetic in the same order, and store the state once. Offline render of that window, 441-frame blocks, median cycles per voice-sample: 16384 voices 3.05 -> 1.12, 32768 voices 4.64 -> 1.13; median callback load 40% -> 14.5% and 153% -> 29%. Filtered bench workloads at 16384 voices: envelope 41.0 -> 28.2% (6 threads) and 20.6 -> 16.0% (20 threads), sustained and release within noise. The filter is still a serial chain per voice; running eight voices in the lanes of one vector is the next step.

- 2026-10-31 `perf(v3): pitch bends step the pitch inside the kernel instead of splitting the span` - a bend used to cut every voice of its channel into one more span, so a bend riser multiplied the kernel entries. The AVX2 per-voice kernels now take a short list of (frame, new fixed-point step) breaks and change the step at that exact frame inside the chunk (the chunk straddling a break takes its eight positions from the old step up to the break and the new one after it), and the row renderer hands consecutive bends of a row to one call. The result is equal to splitting at every bend: the kernel test compares the two over 912 sustained and release cases (90 retiring mid-span) bit for bit, and a block-level test with 160 bends per block gives the same voice state bit for bit and the same audio to 4e-9. Voices the kernels cannot take (vibrato, several voices in one call, scalar and SSE2) split as before. Chopped-notes at 5000 voices, 6 threads, 8000 bends per second: segments per run 10.76 M -> 1.32 M, worker cycles 650 M -> 510 M (-21%); without bends it is unchanged within noise. `SetBendFusion(false)` brings the split path back for comparison.

- 2026-10-31 `fix(v3): releasing voices keep their low-pass filter on spans of 1-4 frames` - the short release kernel (and the scalar release loop used for it) skipped the voice's filter, so a filtered voice in release that event splitting left with 1-4 frames got unfiltered samples for those frames. They are filtered now. This is an audible correction for filtered voices (a click-like brightness blip at splits), found while testing the bend work.

- 2026-10-31 `perf(v3): cheaper per-span setup (FromFloat without llround, MakeFxSteps8 from registers)` - found while chasing why pitch-bend-heavy material got relatively slower: every pitch bend splits the voices of its channel into one more span, so a bend riser multiplies the number of kernel entries (chopped-notes at 5000 voices, 6 threads: 0.57 M spans per second of audio without bends, 10.8 M with 8000 bends per second). The 32.32 conversion had added a library `llround` and a store-then-load-as-vector (a store-forwarding stall) to every span. Both are gone; the results are identical for every positive float. Extra worker cycles caused by the bends, millions: original build 203, after the cursor change 280, now about 290-330 (the whole engine is 30-40% faster, so bends weigh more in relative terms). Not the cause of a big jump; the cost is the number of spans.

- 2026-10-31 `fix(v3): bulk admission thins the notes at the cut evenly, which was a 100 Hz buzz` - listening to the first version on dense chopped notes gave a buzz at the block rate (100 Hz at a 441-frame block). The notes at exactly the cut velocity were dropped earliest-first, so every kept note started near the end of its block and the onsets pulsed at the block rate. They are now thinned with an error-diffusion walk along the block. Block-rate lines in the render of Noise Challenge 2 (first 40 s, 4092 voices), mean dB above the surrounding floor over the first 20 harmonics: 2048-frame block at 100% 11.4 -> 0.7 (exact stealing 1.6); 441-frame block at 100% 4.9 -> 2.7 (exact 2.0), the 100 Hz line itself 4.7 -> 2.8 dB (exact 2.4). `TestBulkAdmission` now checks that the kept share stays within one note of the ideal at every point of the block.

- 2026-10-31 `feat(v3): opt-in bulk block admission (voices.bulk_admission_percent)` - idea taken from reading how Kestrel admits notes (a block's note-ons are ranked and the pool only takes what it can hold). When a block carries more note-on units than the given percentage of the voice limit, the lowest-ranked ones (velocity, ties to the later note) are removed from the event list before the plan, so they never cost a launch; to the note-off pairing it is exactly a note that was launched and stolen unheard. Kept notes keep their exact frames. Default off (0). Chopped black MIDI, 20 threads, staged, events/s: 4092 voices at 15M notes/s 9.11 M exact (328% load) against 125 M with 100% (24% load); 1024 voices at 5M notes/s 7.26 M against 133 M. It changes the sound: Paprika's Noise Challenge 2, first 60 s, 4092 voices, GeneralUser GS, band level against the exact render at 100%: 20-80 Hz +4.6 dB, 2.5-8 kHz -4.3 dB, 8-20 kHz -8.0 dB, whole-file level +0.8 dB; at 800% -0.2 and -0.8 dB at the top bands, 1600% matches within 0.1 dB but drops almost nothing. The short stolen notes are where the high-frequency noise of that piece lives, so the fast settings are a last resort for blocks the exact path cannot finish in time. Pure filter `RenderScalar::BulkAdmissionFilter`, bench switch `--bulk-admission P`, offline env `SVMS_BULK_ADMISSION=P`, `TestBulkAdmission` (filter contract plus RenderBlock equal to the pre-filtered stream, bit for bit).

- 2026-10-31 `feat(v3): staged launches switch on by themselves for pools of 1024 voices or more` - new `voices.launch_staging_auto` (default on, Configurator Performance tab "Staged launches for large pools"). Staging was opt-in because it costs a little on small pools, but chopped black MIDI at 1.5M-5M notes/s, 20 threads, events per second with staging on versus off: 512 voices -6% and -9%, 1024 voices +25% and +27%, 2048 voices +31% and +97%, 4092 voices +41% and +44%, 4096 voices +42% and +46%. - 2026-10-31 `perf(v3): plan thread skips the prefetches launch staging makes useless, and the ghost-tail adoption scan resumes` - with launch staging on, the render jobs write the launch-derived arrays, but every victim still got 30 prefetches for them from the serial plan thread (6% of its samples in a RIP profile at 8192 voices, 5M notes/s). It now pulls only the lines the plan itself reads or writes (steal score inputs, lifecycle row, staged record). Separately, the block-end loop that adopts surviving ghost tails restarted its free-slot scan at 0 for every ghost; it resumes after the last slot taken. Chopped-notes, 5M notes/s, staging on, 20 threads, events per second: 8192 voices 8.53 -> 9.26 M, 65536 voices 4.54 -> 5.54 M (9 interleaved runs each, ranges do not overlap). Staging itself is still opt-in: at 5M notes/s it is +42% at 8192 voices and 65536 voices but -11% at 250 voices.

- 2026-10-31 `perf(v3): cheaper sample fetch for the time-chunk kernels` - with the gain chain fixed, the 20-thread runs on the 13600KF were bound by instructions per sample, not latency. Three things came out of the per-chunk path: (1) at pitch ratio 1 or below the eight lane positions sit within eight samples, so the fetch is two 16-byte loads and a byte shuffle each instead of three widened vectors and a permute/blend ladder; (2) the eight cursor sums come out in frame order from one in-lane shuffle (the step multiples are stored as 0,1,4,5 / 2,3,6,7) instead of four permutes and two lane merges; (3) the callers pass the first and last lane index they already know instead of pulling them out of the vector. Same values, same scale, bit-identical output. 16384 voices, AVX2, G voice-samples per second: sustained 8.25 -> 10.57 at 6 threads and 11.92 -> 15.88 at 20, dense 12.04 -> 15.66 at 20, release 8.90 -> 9.74 at 20, envelope 8.37 -> 9.16 at 20. Release also skips its per-chunk countdown and retire-threshold tests when the gain table proves no chunk of the span can trip them (the gain never rises and the countdown drops one per frame), another 5% at 6 threads and 9% at 20. Going further, a release voice that clears those tests, and an attack/decay voice that stays in its stage for the whole span, render through the sustained kernel's loop with a per-frame gain table (`RenderSustainedChunked<Loop, Tabled>`): the gain is applied before the mix gain, the same order and rounding as before, and the kernel writes the end state (gain, counters) afterwards. Rotated voices keep the general path. Release 9.78 -> 12.35 and envelope 8.82 -> 10.48 G voice-samples per second at 20 threads (6.02 -> 8.02 and 5.13 -> 6.19 at 6).

- 2026-10-31 `perf(v3): envelope gains for eight voices from one vector chain` - the release and the attack/decay gain recurrences are latency-bound chains, about 4 cycles per frame per voice, and release and envelope were limited by exactly that (switching on the closed-form option, which drops the chain, took them 28% and 30% lower). The chains of different voices are independent, so the class entries now run eight voices in the eight lanes of one vector: each lane does the same single multiply (or add), the same clamp selection and the same order per frame as the scalar recurrence, so the tables are bit-identical to it, and the chunk kernels read their eight gains from the table. Voices that change stage inside the span, and the last handles of a batch, keep their own chain. A first version stored the gains and read one back as a scalar, which stalled store forwarding and ate most of the gain, so the kernel takes the last gain straight from the table. 16384 voices, AVX2, 6 threads, cycles per voice-sample: release 0.637 -> 0.516, envelope 0.858 -> 0.651, the rest unchanged. The bench gets a `--fast-chunk-math` switch.

- 2026-10-31 `refactor(v3): one templated time-chunk kernel per envelope stage` - the sustained, release and transient AVX2 time-chunk kernels each existed twice, once for looping and once for one-shot voices, plus the same fetch, lerp, prefetch, vibrato-window and mix code pasted into every copy. They are now `RenderSustainedChunked`, `RenderReleaseChunked` and `RenderTransientChunked` with the loop/one-shot difference as a template parameter, on shared `LerpGather8`, `MixChunk8`, `PrefetchNext` and `VibratoWindow` helpers. Same output, cycles within noise, about 320 fewer lines. The filtered sustained and release group kernels are one `RenderFilteredGroup<Release>` template as well. A first version moved the biquad state into a helper struct and cost the filtered sustained path 4%, so the state stays in plain locals. The three voice-batched short kernels (eight voices per vector) keep their own envelope loops, since they vectorise across voices instead of time, but share `LoopLerp8` for the per-frame wrap, fetch and interpolation.

- 2026-10-31 `perf(v3): release and transient chunks build their gain vector from registers` - the eight gains of a chunk come from eight scalar stores, and one 256-bit load of that array stalled on store forwarding in every chunk; the vector is now assembled from the eight scalars. The transient kernels also run the attack and decay ladders as straight-line code (same recurrence, bit-identical gains) while at least nine counted steps are left. Serial, 8192 voices: release 4.56 to 3.50 cycles per voice-sample, sustained and envelope unchanged within noise. With the fixed-point cursor, AVX2 / 16384 voices / 6 threads against the commit before it (median of 3, interleaved): sustained 0.473 to 0.388, release 0.823 to 0.631, envelope 0.877 to 0.863, chopped-notes 0.587 to 0.506, dense 0.472 to 0.391. The envelope workload stays bound by the exact sequential gain recurrence.

- 2026-10-31 `perf(v3): 32.32 fixed-point voice cursor` - the sample cursor of every voice, steal tail and ghost tail is two uint32 words (index, fraction) instead of one float, with the step derived once per span from the float `phaseIncs` (bend and vibrato still write floats). Integer adds are exact in any order, so the AVX2 chunk kernels compute the eight positions of a chunk in one step (`pos + k * step`) instead of eight dependent float adds, a stored cursor no longer drifts at large sample offsets (the float cursor lost 0.9-3.5 frames over 2048 frames at 16M), and the AVX2 kernels store the cursor already wrapped, so scalar and AVX2 state agree bit for bit. The one-shot kernels no longer fall back to scalar for samples over 16M frames, and the filtered group kernels read their samples with the contiguous loads instead of the gather. The GPU stage (GLSL for OpenGL and Vulkan, CUDA, the offline D3D11 shader) carries the same two words, 9 state words per row, so its cursor stays bit-equal to the scalar one; the interior-run division is gone because the interior/edge test is exact per frame. The scalar path's audio moves by the float cursor's rounding error, so I regenerated the frozen vibrato reference on purpose (`SVMS_DUMP_VIB_GOLDEN=<path>` on svms_v3_correctness captures it from the scalar renderer; the surviving voice set is unchanged). AVX2 at 16384 voices / 6 threads, median of 3 interleaved: sustained 0.547 to 0.506, release 0.917 to 0.891, envelope 1.054 to 1.087 (noise), chopped-notes 0.712 to 0.674, dense 0.550 to 0.508 cycles per voice-sample. The fast-chunk-math differential now passes at the default tolerances, since the oracle no longer drifts.

- 2026-10-27 `feat(v3): same-key recycling for the velocity-lane stealing` - with SVMS_STEAL_PRIORITY a note on a full pool first takes a voice already on its own key, before any other victim: a release tail left on that key once it is under 0.8 of the new level, or the oldest sustained voice on the key when it is not louder, is past its attack and has decayed under half the new level. - 2026-10-27 `feat(v3): velocity-lane voice stealing behind SVMS_STEAL_PRIORITY` - an opt-in victim policy (environment variable for now, off by default, default path unchanged).
